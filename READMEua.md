# Duty Matrix

Модуль графіків чергувань, обліку відсутностей та кадрового планування.
Laravel 11 + Filament v3 (TALL) + PostgreSQL 16 + Redis 7, у Docker.

## Запуск (потрібен встановлений Docker + Docker Compose)

```bash
cp .env.example .env
make init
```

Команда `make init` виконає: збірку образів → підняття контейнерів →
`composer install` → генерацію `APP_KEY` → міграції → сидинг → публікацію
ассетів Filament → `storage:link`.

Після завершення відкрийте: **http://localhost:8080/admin**

## Як влаштована логіка обмежень (ключова частина ТЗ)

`app/Services/ConstraintsEngine.php::validate()` виконує перевірки по черзі
й повертає `ConstraintCheckResult` з одним із трьох статусів:

1. **checkPermission** — чи є запис у `user_event_type_permissions`
2. **checkBlockingExclusivity** — чи не конфліктує з `is_blocking`-подією (в обидва боки)
3. **Перекриття робочих подій** — одній людині не призначаються робочі
   чергування, час яких перетинається, навіть якщо обидва типи не є `is_blocking`
4. **checkCapacity** — чи не перевищено `max_capacity` на дату
5. **evaluateRestPeriod** — рахує відпочинок і ДО, і ПІСЛЯ нової події
   відносно сусідніх подій співробітника, обирає найгірший статус:
   `optimal` (≥ preferred) / `warning` (∈ [min, preferred)) / `forbidden` (< min)

Викликається з `DutyMatrix::createEvent()` при кожному швидкому призначенні
через модальне вікно. При `warning` подія все одно створюється, але з
`has_rest_warning = true` — саме це поле малює ⚠️ у клітинці матриці.

## Що вже працює

- Повна RBAC-модель через Spatie Permission: Admin / Manager / User +
  довільні кастомні ролі з гнучкою матрицею прав (`RoleResource`, лише для Admin)
- Уніфікована модель `user_events` + `event_types` як описано в ТЗ
- Constraints Engine з перевірками допуску, ексклюзивності, перетину робочих
  подій, місткості та відпочинку; покрито тестами
- Матриця чергувань: sticky-колонка, вихідні, кольори типів подій,
  клік по клітинці → модальне швидке призначення, тумблери підсвічування,
  рядок «Непризначено ⚠️» з дефіцитом по `min_capacity`, чернетки позначені
  штрихуванням і позначкою `D`
- Rest zone highlighting при наведенні (Alpine.js, client-side)
- Сторінка звітів: розподіл навантаження, кадровий дефіцит, % винятків
- Excel-експорт з кольорами клітинок і підсумковими колонками
- Redis-кеш для матриці, довідника типів подій і покриття (з інвалідацією при записі)
- **Автогенерація графіка наперед** (`app/Services/AutoScheduler.php` +
  сторінка та модальне вікно «Автогенерація графіка»): за обраний період
  (типово — місяць; у матриці автоматично вибрано її поточний місяць)
  і обрані типи подій (типово — ті, де `min_capacity > 0`) жадібний
  алгоритм зі справедливим балансуванням навантаження розставляє
  співробітників по днях, пропускаючи кожного кандидата через
  `ConstraintsEngine`. Створює лише `draft`-події; дні, які не вдалось
  заповнити (немає допущеного і водночас "прохідного" по обмеженнях
  співробітника), потрапляють у список дефіциту для ручного розбору.
  Можна залишити наявні призначення й заповнити пропуски, видалити та
  перепризначити лише чернетки або видалити всі активні призначення вибраних
  типів подій у періоді. Режими видалення потребують підтвердження; скасовані
  події не видаляються. Менеджер/Admin може затвердити окрему чернетку або всі
  чернетки, видимі в місяці матриці.
  Покрито тестами (`tests/Unit/AutoSchedulerTest.php`).
- **Синергія співробітників**: парна оцінка впливу між двома співробітниками
  зберігається один раз і доступна зі сторінок обох. Вона може діяти для
  вибраних типів подій або для всіх, якщо типи не задані. Під час
  автогенерації система зважено випадково обирає серед співробітників, які
  пройшли обмеження: краща синергія з уже призначеними на цей день дає вищу
  ймовірність, а баланс годин і кількості чергувань зберігає справедливий
  розподіл. Нові пари починаються зі значення `0`; повзунок працює в діапазоні
  `-1…1`, кнопки та числове поле дозволяють задавати будь-які цілі значення.
  Усі створені автогенерацією події, як і раніше, мають статус `draft`.

## Синергія

У таблиці синергій кожен запис описує **неупорядковану пару** співробітників:
значення одне й те саме на сторінках обох людей, а дублікати пари не
створюються. Оцінка `0` є нейтральною; додатне значення підсилює перевагу
спільного чергування, від’ємне — зменшує її. Початковий крок повзунка охоплює
`-1`, `0`, `1`; числове поле і кнопки поруч дають змогу ввести інші цілі
значення. Колір змінюється від червоного для низької оцінки до зеленого для
високої.

На сторінці співробітника є одна таблиця «Синергія»: у ній відображаються
пари як з поточним співробітником A, так і B. Той самий запис видно на
сторінках обох людей, і його можна редагувати чи видалити з будь-якої сторінки.

Виберіть типи подій, для яких слід враховувати оцінку. Якщо список порожній,
вона поширюється на всі типи. Під час заповнення чергування автогенератор
рахує середню оцінку кандидата щодо співробітників, уже призначених на цей
день для вибраних типів подій. Вищі оцінки дають до 100 разів більшу вагу при
випадковому виборі; навантаження в годинах і кількість чергувань зменшують
вагу, щоб зберегти баланс. Випадковий вибір урізноманітнює пари, а перевірки
допуску, відпочинку, місткості та ексклюзивності продовжують застосовуватися
до призначення.

## Одиниця часу: дні або години

Типово інтерфейс працює з цілими днями: події призначаються за датами, а
відпочинок і тривалість зміни вводяться в днях. Кожна подія починається о
00:00 і закінчується о 00:00 дня, наступного за останнім днем події (кінець
не включається). Наприклад, добове чергування 1 вересня зберігається як
`2026-09-01 00:00 – 2026-09-02 00:00`.

У базі значення й надалі зберігаються в годинах (`min_rest_hours`,
`preferred_rest_hours`, `default_duration_hours`, `starts_at`/`ends_at`), а
`App\Support\TimeUnit` перетворює їх для інтерфейсу. Щоб повернути інтерфейс
до годин, задайте в `.env` таке значення й очистьте кеш конфігурації:

```bash
SCHEDULE_TIME_UNIT=hours
php artisan config:clear
```

Міграція `2026_10_29_000000_align_scheduling_data_to_days` вирівнює наявні
дані до цілих днів: відпочинок менше 24 годин стає 0, інші значення
відпочинку й тривалості зміни округлюються вгору до цілих діб, а події
переносяться на початок о 00:00 і кінець о найближчій наступній опівночі.
Ця зміна втрачає точність до годин і не скасовується відкатом міграції.

## Мова інтерфейсу

Інтерфейс доступний українською та англійською мовами. Мова зберігається
глобально в `app_settings` і застосовується до сторінок та форми входу в
адмінпанель. Змінювати її може лише користувач із роллю `Admin`: відкрийте
**Налаштування → Налаштування застосунку**, виберіть мову та збережіть зміни.
Після збереження вибрана мова застосовується до наступних запитів усіх
користувачів.

Вибір мови зберігається під час міграції `2026_10_18_000000_create_app_settings_table`.
Англомовні ключі перекладу та тексти визначені у `lang/en.json`, українські
відповідники — у `lang/uk.json`. Після оновлення застосуйте
міграції командою `php artisan migrate` (або `make init` для нового середовища).
- Docker Compose: app / webserver (nginx) / db (Postgres 16) / redis / worker (queue)
- Makefile з усіма командами з ТЗ п.8.3

## Що варто зробити першим (реалістичний roadmap)

1. **Прогнати `make init` і виправити дрібні неточності складання.**
   Найімовірніші місця: точні назви методів Filament v3 API (деякі методи типу
   `->after('starts_at')` на DateTimePicker, `extraModalFooterActions`) —
   звірте з `composer.lock`-версією `filament/filament`, яку встановить Docker.
2. **Rest zone highlighting зробити повністю серверним/точним** — зараз це
   спрощена Alpine-реалізація на hover; для продакшн-якості варто
   попередньо обчислювати зони на бекенді й віддавати як data-атрибути
   для кожної клітинки одразу (а не лише в момент наведення).
3. **Статус `approved`/затвердження графіка** — модель `status` enum вже є,
   але UI-дії "затвердити місяць" (масова зміна `draft → approved`, доступна
   Manager/Admin) ще не реалізовані — це явно згадано в ТЗ п.2.1.
4. **Автогенерація: перенести у чергу (queue worker)** — зараз рахує
   синхронно в HTTP-запиті; для великих періодів/штату (сотні людей × рік)
   варто dispatch'ити `Job`, який вже готовий інфраструктурно
   (`docker-compose worker`-контейнер уже піднятий і чекає), і показувати
   прогрес через Livewire-поллінг або database-нотифікацію по завершенню.
5. **Drag-and-drop переміщення подій** у матриці (зараз лише клік → модалка) —
   природне розширення Livewire-компонента з `wire:drag`/Alpine або SortableJS.
5. **Тести Feature-рівня** на Filament-ресурси й Policy (зараз є лише Unit-тести
   Constraints Engine).
6. **Продуктивність на 50×31**: перевірити реальний час рендеру великої матриці
   і за потреби пагінувати/лінивого підвантажувати місяці замість повного eager load.

## Якщо щось не запускається

```bash
make logs-app        # логи PHP-контейнера
make shell            # зайти всередину і подивитись помилку вручну
docker compose exec app php artisan about   # перевірити конфігурацію Laravel
docker compose exec app composer show filament/filament   # яка версія встановилась
```

Найчастіша причина падіння на першому запуску — розбіжність версій
`filament/filament`.
Якщо `composer install` підтягне новішу мажорну версію з іншим API —
звузьте версію в `composer.json` до конкретного релізу 3.x, з яким писався код.
