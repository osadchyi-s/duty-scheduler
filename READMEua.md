# Duty Matrix

Модуль графіків чергувань, обліку відсутностей та кадрового планування.
Laravel 11 + Filament v3 (TALL) + PostgreSQL 16 + Redis 7, у Docker.

## Запуск (потрібен встановлений Docker + Docker Compose)

```bash
cp .env.example .env
make init
```

Команда `make init` виконає: збірку образів → підняття контейнерів →
`composer install` → генерацію `APP_KEY` → міграції → сидинг → публікацію
ассетів Filament → `storage:link`.

Після завершення відкрийте: **http://localhost:8080/admin**

## Як влаштована логіка обмежень (ключова частина ТЗ)

`app/Services/ConstraintsEngine.php::validate()` виконує перевірки по черзі
й повертає `ConstraintCheckResult` з одним із трьох статусів:

1. **checkPermission** — чи є запис у `user_event_type_permissions`
2. **checkBlockingExclusivity** — чи не конфліктує з `is_blocking`-подією (в обидва боки)
3. **Перекриття робочих подій** — одній людині не призначаються робочі
   чергування, час яких перетинається, навіть якщо обидва типи не є `is_blocking`
4. **checkCapacity** — чи не перевищено `max_capacity` на дату
5. **Ліміти чергувань** — кількість днів чергувань співробітника в кожному
   вікні періоду не перевищує лімітів його груп (див.
   [Ліміти чергувань](#ліміти-чергувань)). Жорсткий ліміт забороняє
   призначення, м’який додає попередження.
6. **evaluateRestPeriod** — рахує відпочинок і ДО, і ПІСЛЯ нової події
   відносно сусідніх подій співробітника, обирає найгірший статус:
   `optimal` (≥ preferred) / `warning` (∈ [min, preferred)) / `forbidden` (< min).
   Правила відпочинку діють на період ПІСЛЯ події: перерва між двома подіями
   перевіряється лише за правилами типу ранішої події. Наприклад, якщо тип
   події вимагає одну добу відпочинку, наступний день має бути вільним, а
   попередній день може бути зайнятим.

Викликається з `DutyMatrix::createEvent()` при кожному швидкому призначенні
через модальне вікно. При `warning` (відпочинок або м’який ліміт) подія все
одно створюється, але з `has_warning = true` — саме це поле малює ⚠️ у
клітинці матриці.

## Що вже працює

- Повна RBAC-модель через Spatie Permission: Admin / Manager / User +
  довільні кастомні ролі з гнучкою матрицею прав (`RoleResource`, лише для Admin)
- Уніфікована модель `user_events` + `event_types` як описано в ТЗ
- Constraints Engine з перевірками допуску, ексклюзивності, перетину робочих
  подій, місткості та відпочинку; покрито тестами
- Матриця чергувань: sticky-колонка, вихідні, кольори типів подій,
  клік по клітинці → модальне швидке призначення, тумблери підсвічування,
  рядок «Непризначено ⚠️» з дефіцитом по `min_capacity`; для адміністраторів
  і менеджерів — вкладки чернеток місяця (див. [Чернетки графіка](#чернетки-графіка))
- Rest zone highlighting при наведенні (Alpine.js, client-side)
- Сторінка звітів: розподіл навантаження, кадровий дефіцит, % винятків
- Excel-експорт з кольорами клітинок і підсумковими колонками
- Redis-кеш для матриці, довідника типів подій і покриття (з інвалідацією при записі)
- **Автогенерація графіка наперед** (`app/Services/AutoScheduler.php` +
  сторінка та модальне вікно «Автогенерація графіка»): за обраний період у
  межах одного місяця і обрані типи подій (типово — ті, де `min_capacity > 0`)
  жадібний алгоритм зі справедливим балансуванням навантаження розставляє
  співробітників по днях, пропускаючи кожного кандидата через
  `ConstraintsEngine`. Генерує завжди в чернетку графіка (нову або вибрану),
  а не одразу в затверджений графік. Дні, які не вдалось заповнити (немає
  допущеного і водночас "прохідного" по обмеженнях співробітника),
  потрапляють у список дефіциту для ручного розбору. Можна залишити наявні
  призначення чернетки й заповнити пропуски або видалити й перепризначити
  призначення вибраних типів подій у періоді; скасовані події не видаляються.
  Покрито тестами (`tests/Unit/AutoSchedulerTest.php`).
- **Синергія співробітників**: парна оцінка впливу між двома співробітниками
  зберігається один раз і доступна зі сторінок обох. Вона може діяти для
  вибраних типів подій або для всіх, якщо типи не задані. Під час
  автогенерації система спершу залишає серед співробітників, які пройшли
  обмеження, лише найменш завантажених у годинах, а потім зважено випадково
  обирає з них: краща синергія з уже призначеними на цей день дає вищу
  ймовірність, а більша кількість чергувань цього типу її зменшує. Оцінка задається перемикачем із трьома станами: негативна (`-1`,
  червона), нейтральна (`0`, сіра) або позитивна (`1`, зелена). Нові пари
  починаються з нейтрального значення.
- **Ліміти чергувань** для груп співробітників: максимальна кількість днів
  чергувань на співробітника за календарний тиждень, календарний місяць,
  фіксований або повторюваний період — як жорсткий або м’який ліміт.

## Синергія

У таблиці синергій кожен запис описує **неупорядковану пару** співробітників:
значення одне й те саме на сторінках обох людей, а дублікати пари не
створюються. Оцінка має три стани: `1` (позитивна) підсилює перевагу
спільного чергування, `-1` (негативна) зменшує її, а `0` (нейтральна) не
впливає. Записи, створені до появи перемикача, можуть містити інші цілі
значення; інтерфейс показує їх за знаком.

На сторінці співробітника є одна таблиця «Синергія»: у ній відображаються
пари як з поточним співробітником A, так і B. Той самий запис видно на
сторінках обох людей, і його можна редагувати чи видалити з будь-якої сторінки.

Виберіть типи подій, для яких слід враховувати оцінку. Якщо список порожній,
вона поширюється на всі типи. Під час заповнення чергування автогенератор
спершу залишає лише допущених співробітників із найменшим навантаженням у
годинах, щоб зберегти баланс. Серед них він рахує середню оцінку кандидата
щодо співробітників, уже призначених на цей день для вибраних типів подій.
Вищі оцінки дають до 100 разів більшу вагу при випадковому виборі, а більша
кількість чергувань цього типу вагу зменшує. Випадковий вибір урізноманітнює пари, а перевірки
допуску, відпочинку, місткості та ексклюзивності продовжують застосовуватися
до призначення.

## Чернетки графіка

Можна готувати кілька варіантів графіка місяця одночасно. У матриці
чергувань адміністратори й менеджери бачать вкладку **Затверджений графік** і
по вкладці на кожну чернетку показаного місяця. Звичайні співробітники бачать
лише затверджений графік.

- **Нова чернетка** копіює в нову чернетку затверджені події місяця (зокрема
  ті, що переходять через межу місяця).
- **Автогенерація** у вкладці затвердженого графіка створює нову чернетку й
  генерує в неї; у вкладці чернетки — генерує в цю чернетку. Генерація по
  одній чернетці не перевантажує систему; кількість чернеток не обмежена.
- Події чернетки редагуються в матриці так само, як затверджені. Усі
  перевірки (відпочинок, перекриття, місткість, ліміти чергувань) виконуються
  щодо подій чернетки плюс затверджених подій поза її місяцем, тож правила на
  межі місяців теж діють.
- Меню **Чернетка** дає змогу перейменувати, продублювати або видалити
  чернетку. **Очистити чернетку** видаляє всі її події. Експорт в Excel
  вивантажує поточну вкладку.
- **Затвердити чернетку** замінює затверджені події місяця, типи яких беруть
  участь в автогенерації (`is_schedulable`), подіями чернетки. Інші події,
  наприклад відпустки чи лікарняні, лишаються завжди. Затверджені події, яких
  немає в чернетці, показуються списком, і будь-які з них можна залишити.
  Кожна нова подія перевіряється в підсумковому графіку; якщо хоч одне
  призначення заборонене, нічого не змінюється, а проблеми показуються
  списком.
- Після затвердження інші чернетки місяця позначаються як **Застаріла**.
  Вони зберігаються, і їх можна затвердити пізніше; форма затвердження тоді
  покаже різницю з поточним графіком.

Чернетки зберігаються в таблиці `schedule_drafts`, а їхні події — рядки
`user_events` із заповненим `schedule_draft_id` (`NULL` означає затверджений
графік) і `source_event_id`, що вказує на затверджену подію, з якої зроблено
копію. Термін життя чернеток не обмежений. Міграція
`2026_10_31_000002_move_draft_events_into_schedule_drafts` переносить події з
колишнім статусом `draft` у чернетку «Перенесені чернетки» їхнього місяця.
Статистика будується лише за затвердженим графіком.

Типи подій і співробітників, у яких є події, видалити не можна —
деактивуйте їх, щоб зберегти історію графіка.

## Ліміти чергувань

Ліміти обмежують, скільки днів чергувань може мати кожен співробітник за
період. Вони складаються з трьох сутностей, кожна з яких має окрему сторінку,
доступну адміністраторам і менеджерам:

- **Групи співробітників** (**Кадри та доступ → Групи співробітників**) —
  іменовані набори співробітників. Один співробітник може входити в кілька
  груп.
- **Періоди** (**Правила графіка → Періоди**) — вбудовані *календарний
  тиждень* (з понеділка по неділю) і *календарний місяць* доступні завжди й
  не редагуються. Можна додати *фіксований період* (діапазон дат) або
  *повторюваний період* (наприклад, 7 днів кожні 14 днів від певної дати).
  Період, який використовує ліміт, видалити не можна.
- **Ліміти чергувань** (**Правила графіка → Ліміти чергувань**) — період,
  групи співробітників, максимальна кількість днів чергувань на співробітника
  та дія при перевищенні: заборонити призначення або дозволити з
  попередженням. Якщо типи подій не вибрано, враховуються всі робочі типи.
  Групу й період можна створити прямо з форми ліміту.

Ліміт діє окремо для кожного співробітника вибраних груп у кожному вікні
періоду. Перевіряються всі ліміти, що стосуються співробітника, тож фактично
діє найсуворіший. Подія рахується стільки днів, скільки триває, починаючи з
дня початку; багатоденна подія ділиться між вікнами. У режимі годин 24-годинна
зміна рахується за день, у який починається.

Ліміти перевіряє Constraints Engine, тому вони діють і під час ручного
призначення, і в автогенерації. Матриця також позначає ⚠️ наявні події, що
перевищують ліміт, зокрема створені до появи ліміту; причина видна в
підказці.

Нові типи періодів додаються реалізацією `App\Periods\PeriodType` і
реєстрацією класу в `App\Periods\PeriodTypes`; міграція для цього не
потрібна.

## Одиниця часу: дні або години

Типово інтерфейс працює з цілими днями: події призначаються за датами, а
відпочинок і тривалість зміни вводяться в днях. Кожна подія починається о
00:00 і закінчується о 00:00 дня, наступного за останнім днем події (кінець
не включається). Наприклад, добове чергування 1 вересня зберігається як
`2026-09-01 00:00 – 2026-09-02 00:00`.

У базі значення й надалі зберігаються в годинах (`min_rest_hours`,
`preferred_rest_hours`, `default_duration_hours`, `starts_at`/`ends_at`), а
`App\Support\TimeUnit` перетворює їх для інтерфейсу. Щоб повернути інтерфейс
до годин, задайте в `.env` таке значення й очистьте кеш конфігурації:

```bash
SCHEDULE_TIME_UNIT=hours
php artisan config:clear
```

Міграція `2026_10_29_000000_align_scheduling_data_to_days` вирівнює наявні
дані до цілих днів: відпочинок менше 24 годин стає 0, інші значення
відпочинку й тривалості зміни округлюються вгору до цілих діб, а події
переносяться на початок о 00:00 і кінець о найближчій наступній опівночі.
Ця зміна втрачає точність до годин і не скасовується відкатом міграції.

## Мова інтерфейсу

Інтерфейс доступний українською та англійською мовами. Мова зберігається
глобально в `app_settings` і застосовується до сторінок та форми входу в
адмінпанель. Змінювати її може лише користувач із роллю `Admin`: відкрийте
**Налаштування → Налаштування застосунку**, виберіть мову та збережіть зміни.
Після збереження вибрана мова застосовується до наступних запитів усіх
користувачів.

Вибір мови зберігається під час міграції `2026_10_18_000000_create_app_settings_table`.
Англомовні ключі перекладу та тексти визначені у `lang/en.json`, українські
відповідники — у `lang/uk.json`. Після оновлення застосуйте
міграції командою `php artisan migrate` (або `make init` для нового середовища).
- Docker Compose: app / webserver (nginx) / db (Postgres 16) / redis / worker (queue)
- Makefile з усіма командами з ТЗ п.8.3

   для кожної клітинки одразу (а не лише в момент наведення).
3. **Затвердження графіка** — реалізовано через чернетки графіка (див.
   [Чернетки графіка](#чернетки-графіка)).
4. **Автогенерація: перенести у чергу (queue worker)** — зараз рахує
   синхронно в HTTP-запиті; для великих періодів/штату (сотні людей × рік)
   варто dispatch'ити `Job`, який вже готовий інфраструктурно
   (`docker-compose worker`-контейнер уже піднятий і чекає), і показувати
   прогрес через Livewire-поллінг або database-нотифікацію по завершенню.
5. **Drag-and-drop переміщення подій** у матриці (зараз лише клік → модалка) —
   природне розширення Livewire-компонента з `wire:drag`/Alpine або SortableJS.
5. **Тести Feature-рівня** на Filament-ресурси й Policy (зараз є лише Unit-тести
   Constraints Engine).
6. **Продуктивність на 50×31**: перевірити реальний час рендеру великої матриці
   і за потреби пагінувати/лінивого підвантажувати місяці замість повного eager load.

## Якщо щось не запускається

```bash
make logs-app        # логи PHP-контейнера
make shell            # зайти всередину і подивитись помилку вручну
docker compose exec app php artisan about   # перевірити конфігурацію Laravel
docker compose exec app composer show filament/filament   # яка версія встановилась
```

Найчастіша причина падіння на першому запуску — розбіжність версій
`filament/filament`.
Якщо `composer install` підтягне новішу мажорну версію з іншим API —
звузьте версію в `composer.json` до конкретного релізу 3.x, з яким писався код.
